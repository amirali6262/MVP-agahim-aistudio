# نقشه راه محصول آگاهیم

## هدف محصول

آگاهیم یک ERP عمومی نیست؛ «سیستم‌عامل تعهدات قانونی کسب‌وکار» است. ادمین پلتفرم قانون، مشمولیت، فرایند، فرم، مهلت و هشدار را طراحی و منتشر می‌کند. کاربر فقط باید بداند چه کاری، چرا، تا چه زمانی و با چه مدارکی انجام دهد.

معماری MVP به‌صورت Modular Monolith باقی می‌ماند تا ماژول‌ها جدا و قابل توسعه باشند، بدون هزینه و پیچیدگی Microservice.

## وضعیت فعلی

| بخش | وضعیت | توضیح ساده |

| Vite، React و TypeScript | موجود | Build و TypeScript فعال است. |
| احراز هویت Supabase | موجود | ثبت‌نام، تأیید ایمیل و ورود کاربر/مدیر جدا شده است (بدون Mock). |
| Tenant و عضویت | موجود | شرکت و مالک به‌صورت اتمیک ساخته می‌شوند و RLS جداسازی را اعمال می‌کند. |
| CI و بررسی Secret | موجود | Build، TypeScript، Audit و الگوهای Credential بررسی می‌شوند. |
| Typeهای واقعی Supabase | در PR مستقل | Client، جدول‌ها و RPC از دیتابیس واقعی Type می‌شوند. |
| کاتالوگ تعهدات و Workflow | موجود | جدول‌های obligation/obligation_definition و Workflow واقعی هستند و از Supabase خوانده می‌شوند. |

| فرایند هیأت حل اختلاف بدوی | موجود | ۹ مرحله و ۱۲ انتقال به‌عنوان داده مرجع ثبت شده‌اند. |
| موتور مهلت | موجود | قواعد مهلت با تقویم ایران و توابع محاسبه/انتساب مهلت در دیتابیس تعریف شده‌اند. |
| اعلان، ایمیل و پیامک | در حال برنامه‌ریزی | ارسال واقعی به فاز بعد منتقل شده است. |

## فاز صفر — تثبیت پایه

### 0.1 امنیت و Tenant — انجام‌شده

- Auth و Trigger ساخت پروفایل
- RLS برای مالک، مدیر، عضو و کاربر خارج از شرکت
- جلوگیری از دسترسی بین شرکت‌ها
- RPC اتمیک ساخت شرکت و مالک
- CI، Audit و بررسی Credential

### 0.2 Type Safety — در حال انجام

- تولید Type از دیتابیس واقعی
- Type کردن Supabase Client، جدول‌ها و RPC
- حذف یا توقف امن Queryهایی که جدول واقعی ندارند
- معیار پذیرش: TypeScript، Build، Audit و CI موفق

### 0.3 پاک‌سازی مرز Mock و Production — انجام‌شده

- تمام fallbackهای Mock/Demo از کد حذف شده‌اند؛ همه‌چیز مستقیم از Supabase خوانده می‌شود و در نبود اتصال، fail-closed است.
- دادهٔ نمونه/آزمایشی کاتالوگ از دیتابیس غیرفعال شده است (رجوع به migration حذف داده نمونه).

## فاز یک — هسته پویای تعهدات

هر مورد زیر یک PR مستقل خواهد بود.

### 1.1 پروفایل جامع و تاریخ‌دار کسب‌وکار — P0

- نوع شخصیت، فعالیت، ثبت مالیاتی، ارزش افزوده، تعداد کارکنان، فروش، شعب، قراردادها و حقوق
- ثبت تاریخ شروع و پایان اعتبار اطلاعات مؤثر بر مشمولیت
- RLS کامل برای اعضای همان شرکت

### 1.2 کاتالوگ تعهدات و نسخه قانون — P0

- خانواده تعهد، عنوان، مرجع رسمی و لینک اقدام
- نسخه‌های پیش‌نویس، بازبینی، آزمایش، منتشرشده و منسوخ
- نسخه منتشرشده غیرقابل ویرایش؛ اصلاح فقط با نسخه جدید

### 1.3 موتور مشمولیت — P0

- Decision Table محدود، بدون SQL یا کد آزاد
- نتیجه: مشمول، غیرمشمول، یا نیازمند بررسی
- ذخیره دلیل تصمیم و نسخه قاعده
- هوش مصنوعی حق انتشار خودکار قاعده حقوقی ندارد

### 1.4 Workflow و فرم محدود — P0

- مراحل، ترتیب، مسئول، مدارک، فیلدها و شاخه‌های کنترل‌شده
- قالب‌های آماده به‌جای BPMN آزاد
- نسخه‌بندی Workflow و فرم

### 1.5 پرونده و وظیفه — P0

- ایجاد خودکار پرونده برای شرکت مشمول
- نمایش فقط مرحله فعال و اقدام بعدی به کاربر
- ثبت رسید، تاریخچه تغییرات و Audit Log

## وابستگی اجرای فازها

```text
پروفایل کسب‌وکار
  → کاتالوگ و نسخه قانون
    → موتور مشمولیت
      → Workflow و فرم
        → پرونده و وظیفه
          → داشبورد و تقویم
            → اعلان و بخشنامه
              → جریمه، اعتراض و گزارش
```

## قواعد تحویل GitHub-first

- هر قابلیت در شاخه و Draft PR مستقل ساخته می‌شود.
- بعد از هر بخش سالم، حداکثر طی ۴۵ دقیقه Commit و Push انجام می‌شود.
- تست هدفمند در checkpointها و تست کامل پیش از Merge اجرا می‌شود.
- کد ناقص وارد `main` نمی‌شود، اما روی Draft PR از بین نمی‌رود.
- وضعیت هر PR شامل انجام‌شده، مرحله بعد و Blocker است.
- Secret، داده واقعی حساس و کلید مدیریتی وارد Git نمی‌شود.
- Merge فقط با CI موفق و بدون مشکل امنیتی حل‌نشده انجام می‌شود.

## توقف‌های اجباری

کار فقط برای هزینه یا خرید سرویس، انتشار Production، ارسال واقعی انبوه، حذف داده، Secret جدید، انتشار قاعده حقوقی تأییدنشده یا تغییر اساسی مدل تجاری/ظاهر متوقف می‌شود.
